M Track M — ยกระดับ ML Training (งานใหญ่)

เป้าหมาย: จากโมเดล "พอใช้ได้ 20 จังหวัด" → ครบ 77 จังหวัด และ เก่งระดับ production. หัวใจที่วัดมาแล้ว: โมเดลปัจจุบัน "ตาบอดต่อพยากรณ์ของวันที่มันทำนาย" — และ forecast covariate คือคันโยกเดียวที่พิสูจน์แล้วว่าได้ผล.

3.1 สถานะตรงไปตรงมา

โมเดลขอบเขตคะแนน (test)สถานะ
v1 Open-Meteo20 จว. · 1991–2025F2 0.556 · ROC 0.76บน production
v2 ERA5 (clean)77 จว. · 2016–2025F2 0.317 · ROC 0.62สะอาด/ทำซ้ำได้ แต่คะแนนต่ำกว่า (ประวัติสั้น)
เพดาน oracle (รู้อนาคต)—F2 0.915 · PR-AUC 0.88headroom: forecast covariate เท่านั้นที่ไปถึง
📈
คันโยกที่พิสูจน์แล้วด้วยข้อมูลจริง (GEFS reforecast): เพิ่ม forecast heat-index ของวันเป้าหมาย → ROC 0.578 → 0.657 (+0.079), PR-AUC lift 1.22×→1.82×. lift แรงสุดที่ lead 3–5 (persistence จัดการ lead 1 อยู่แล้ว). รายละเอียด: docs/MODEL-IMPROVEMENT.md §5

3.2 ทำไม v2 (77 จว.) ถึงคะแนนต่ำกว่า — และทางออก

ไม่ใช่ข้อมูลแย่ แต่การบังคับมีความชื้น (ERA5) ทำให้เหลือประวัติแค่ 2016+ → เสีย 27 ปี และปีฝึกเย็นกว่าปีทดสอบ (positive rate 2.6%→8.1%). ทางออกคือ multi-fidelity: ใช้ t2m ยาว (1991+) เป็นแกน antecedent + ฟีเจอร์ความชื้นเฉพาะที่มี.

3.3 Roadmap เป็นเฟส (พร้อมเหตุผล + effort)

M1

Forecast covariate → wire เข้า production training คันโยกหลัก

ME · ขึ้นกับข้อมูล hindcast
  • เหลือรอ: collector (กำลังรันทุกวัน) สะสม Open-Meteo forecast ให้ครอบคลุมหน้าร้อน (~2–3 เดือน) → ได้ hindcast ที่ match แหล่ง serve-time
  • แล้ว join เข้า forecasting frame ที่ target_date → เทรนใหม่ด้วย fc_heat_index เป็นฟีเจอร์
  • ผลคาด: ROC 0.6→0.66+ ที่ lead 3–5, precision ดีขึ้น (false alarm ลด)
  • ทางลัดวัดผลทันที (ไม่ต้องรอ): GEFS reforecast 2016–2019 (ทำไว้แล้ว) — ใช้ประเมิน per-lead ก่อนตัดสินใจ productionize
M2

ขยาย production 20 → 77 จังหวัด DECISION

  • ตัวเลือก A: สลับ production ไปใช้ v2 (77 จว. ครบเลย แต่คะแนน antecedent ต่ำกว่า)
  • ตัวเลือก B (แนะนำ): multi-fidelity — t2m ยาว 1991+ ทุกจังหวัด เป็นแกน + humidity features เฉพาะที่มี → ครบ 77 โดยไม่เสียประวัติ
  • ผลพลอยได้: แผนที่ลงสีครบ 77 จังหวัด (ตอนนี้ 20)
M3

Label robustness — fixed-baseline p95

  • fit per-province p95 บน baseline ปีฝึกคงที่ (ไม่ให้ threshold ดูดซับ warming trend) → ลด train→test label shift
  • effort ต่ำ, ลดความผันผวนของคะแนนข้ามปี
M4

งานรายภูมิภาค (skill ไม่สม่ำเสมอ)

  • South F2 0.70 vs Northeast 0.39, West 0.40, Chiang Rai 0.10 (base rate 1.4%)
  • per-region threshold, ฟีเจอร์เฉพาะภาค (เหนือแห้งต่างจากใต้), หรือ pool จังหวัด base rate ต่ำมาก
M5

Operating point กับ stakeholder

  • ตอนนี้ precision 0.23 = false alarm เยอะ (จุด F2 เน้น recall)
  • เลือกจุดจากต้นทุนจริงของ "เตือนผิด" vs "พลาดคลื่นร้อน"; พิจารณา 2 ระดับ (watch / warning)
M6

Retrain → promote → automate (ปิดลูป) artifact story

  • ตัดสิน artifact story: train-in-CI หรือ ดาวน์โหลดโมเดลจาก HF/Release
  • ตั้ง GitHub Action cron รัน run_daily_forecast.py + secrets (DATABASE_URL) — เลิกพึ่ง Task Scheduler ในเครื่อง

3.5 วิธีทำงาน (methodology)

  • Ablate ทีละสัญญาณ: เพิ่ม 1 ฟีเจอร์ → วัด ΔPR-AUC บน split เดิม เก็บเฉพาะที่ขยับจริง
  • เชื่อตัวเลขด้วย rolling-origin CV (scripts/cv_era5.py) ไม่ใช่ปีเดียว (base rate แกว่ง 3%→13%)
  • Stop rule: "พอแล้ว" = ชนะ baseline (climatology F2 0.47) ที่ operating point ที่ stakeholder รับได้
