1 · ภาพรวม

โปรเจคนี้คืออะไร

พยากรณ์ว่าจะเกิด “คลื่นความร้อน” ในแต่ละจังหวัดล่วงหน้า 1–7 วัน แล้วสื่อสารเป็น สีความเสี่ยงบนแผนที่ + การแจ้งเตือน 2 ระดับ (เฝ้าระวัง/เตือนภัย) ผ่านแอปและ LINE · 4 codebase อยู่โฟลเดอร์ราก เดียวกัน:

🧮 ML / Forecasting — Python

เทรนโมเดล + รัน forecast รายวัน · src/*.py, pipeline/, scripts/, evaluation/

🦊 Backend — Elysia + Bun

เสิร์ฟ API ดึงผลจาก Supabase + LINE bot · src/index.ts, src/routes/, src/line/

📱 Frontend — Expo / React Native

แอปแผนที่/แจ้งเตือน/ความปลอดภัย · HeatMAP-Frontend/

📊 Training Dashboard — local

FastAPI + Vite UI เทรนสด (sandbox) · training-dashboard/

⚠️ จุดสับสนที่ควรรู้: โฟลเดอร์ src/ ปนกัน — มีทั้งโมดูล ML (Python) และ backend (TypeScript) อยู่ที่เดียวกัน · package.json ราก = ของ backend ไม่ใช่ ML
2 · หัวใจของระบบ

การพยากรณ์แบบ “ไม่รั่ว” (leakage-safe)

นี่คือดีไซน์ที่สำคัญที่สุด — โปรเจคนี้เกิดใหม่เพราะเวอร์ชันก่อนเคย “โกง” (ได้คะแนนปลอม ~0.99) จากการรั่วของข้อมูล กฎเหล็ก 4 ข้อ:

🔒 1. Features ย้อนหลังล้วน

ทุกฟีเจอร์สร้างด้วย .shift(1).rolling(...) — ค่าของวันนี้ ห้ามเข้าไปในฟีเจอร์ของตัวเอง · target = y = heatwave.shift(-k) (คลื่นความร้อนอีก k วัน) · มี LEAKY_COLS กันคอลัมน์ความจริงของวันเป้าหมายหลุดเป็นฟีเจอร์

📅 2. แบ่งข้อมูลตามเวลา

train ปีเก่า / val-test ปีใหม่ (train ≤2023 · val 2024 · test 2025) · ห้าม random split เพราะอากาศรายวัน autocorrelated → random = รั่ว = คะแนนปลอม

🎯 3. Calibrate + จูน threshold

isotonic calibration ให้ความน่าจะเป็น “ตรงจริง” + จูน threshold ด้วย F2 บน validation (src/calibration.py) — ไม่ใช้ SMOTE (ทำลาย calibration ของ rare event)

📏 4. วัดผลแบบ rare-event

ใช้ PR-AUC / F2 / Brier (ไม่ใช่ accuracy) · normalize PR-AUC ด้วย base rate ก่อนเทียบข้ามปี (เพราะ ~4–14% positive)

🚫 ERA5 / Open-Meteo “historical forecast” = การวิเคราะห์ (ความจริง) ไม่ใช่คำพยากรณ์อนาคต — ใช้เป็นฟีเจอร์ย้อนหลังได้ แต่ถ้าเอา “ความจริงของวันเป้าหมาย” มาเป็นฟีเจอร์ = รั่วทันที

นิยาม label (src/labels.py, src/climatology.py): คลื่นความร้อน = sWBGT ≥ p95 ของวันนั้นในรอบปี (climatology 1991–2020) และ เป็นช่วงร้อนต่อเนื่อง ≥ 2 วัน · sWBGT คำนวณจาก temp + ความชื้น (src/swbgt.py)

3 · เลือกโมเดล

ทำไมถึงเลือก LightGBM

scripts/bakeoff.py เทรนทุกตัวบน frame / temporal split / calibration / F2-tuning ชุดเดียวกัน แล้วจัดอันดับด้วย F2 → PR-AUC (BSS เป็น tiebreak):

เหตุผล (จาก docs/ML-APPROACH.md):

  • Tree ensemble ชนะบน tabular rare-event — deep nets (MLP/KAN) ไม่ช่วยและช้า; KAN ใช้กับ ~1M แถวไม่ได้
  • 3 ตัวบนเสมอกันเชิงสถิติ (balanced_rf / lightgbm / catboost) — LGBM ไม่ได้ทิ้งห่าง
  • ตัวชี้ขาด = generalization: บน validation หลากหลายกว่า (3 จังหวัด รวมใต้+อีสาน) LightGBM นำ F2 0.58 → สกิลโตตามความครอบคลุม
  • ปฏิบัติจริง: เร็ว, สเกลถึง ~1M แถว, เข้ากับ pipeline calibration/threshold ได้สะอาด
ตัดสินใจ: Primary = LightGBM · track balanced_rf + catboost เป็นทางเลือก · ensemble เป็น robustness · เลือกตัวสุดท้ายด้วย F2 → PR-AUC → BSS บน multi-province leaderboard

5 · Input ของโมเดล

โมเดลต้องมี input ทุกครั้งที่ทำนาย

โมเดลคือ “ฟังก์ชัน” ไม่ใช่ตารางค่าตายตัว ต่อ 1 จังหวัดต้องป้อน 4 อย่าง:

🌡️ ประวัติ 40 วัน (ERA5) — สร้างฟีเจอร์ rolling
🔮 พยากรณ์ 8 วัน — ให้ sWBGT วันเป้าหมาย
📈 p95 climatology — เกณฑ์ความร้อนรายวัน
📦 heatwave_model.pkl — ฟังก์ชันที่เทรนไว้
ฟีเจอร์เป็น antecedent-only จึงต้องมีประวัติ ~40 วันเพื่อคำนวณ rolling window — ไม่มี input ชุดนี้ ทำนายไม่ได้เลย
6 · Product จริง (3 layer)

Backend · Frontend · LINE · Database

🦊 Backend API (Elysia + Bun) — อ่านจาก Supabase

GET/api/forecast/map — ค่าเสี่ยงล่าสุดทุกจังหวัด (สำหรับแผนที่)
GET/api/forecast/province/:id — พยากรณ์ 7 วันของจังหวัดเดียว
GET/api/provinces — รายชื่อ 77 จังหวัด
GET/api/thresholds/:id — เกณฑ์ p95 รายจังหวัด
GET/api/health — health check
POST/api/line/webhook — LINE Messaging API (verify ลายเซ็น HMAC)

📱 Frontend (แอป) — 4 หน้า

  • Map — grid 77 จังหวัดลงสีตามความเสี่ยง + การ์ด “พื้นที่ของคุณ” (GPS) + สถานะ loading/ไม่มีข้อมูล
  • Alerts — สรุปทั้งประเทศ 2 ระดับ (เฝ้าระวัง/เตือนภัย) + พยากรณ์ราย จังหวัด 7 วัน
  • Safety (checklist) — เช็กลิสต์รับมือ + เบอร์ฉุกเฉิน
  • Profile (settings) — ธีม/ภาษา/ฟอนต์/แจ้งเตือน

+ หน้า liff สำหรับเปิดในแอป LINE

💬 LINE Bot (src/line/)

  • signature — ตรวจลายเซ็น HMAC-SHA256 ของ webhook
  • webhook — รับ event แล้วตอบ
  • flex / push — ส่งการ์ดพยากรณ์ (Flex message)
  • nearest — หาจังหวัดใกล้ผู้ใช้ · richmenu — เมนูลัด
🗄️ Database (Supabase): ข้อมูลอยู่ใน schema ส่วนตัว heatwave (ไม่เปิดผ่าน Data API) · backend ต่อด้วย postgres (Bun) · Python เขียนด้วย psycopg (src/db_write.py)
เกณฑ์สี (ตรงกันทั้ง src/risk.py และ frontend): moderate ≥ 0.10 · high/เฝ้าระวัง ≥ 0.217 · extreme/เตือนภัย ≥ 0.281
7 · เทรนใหม่ตอนไหน

“รันรายวัน” ≠ “เทรนใหม่”

🔁 รันรายวัน — ใช้โมเดลเดิม ไม่เทรน

  • โหลด heatwave_model.pkl เดิม → ป้อนอากาศล่าสุด → ได้ค่าใหม่
  • เปลี่ยนแค่ input ไม่แตะพารามิเตอร์โมเดล
  • ควรรันทุกวันให้แผนที่สด — ตอนนี้ยัง DORMANT
